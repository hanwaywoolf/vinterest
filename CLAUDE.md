## Process
- The version shown in Wine DNA (below Data Backup) is generated at build time as `<package.json version> (<build number> · <commit>)`, e.g. `v1.3.0 (214 · 2ba108e)`, so every deploy is identifiable without a manual bump. Don't hand-edit a version string into `pwa-screens-wineiq.jsx`; it renders `__APP_VERSION__`. Bump `version` in `package.json` only for a release worth naming. The build number is `BUILD_NUMBER` if set, otherwise the commit count on HEAD; a shallow clone shows the commit alone.
- Run `npm run test:db` after changing anything in `supabase/` (needs a local Postgres).
- GitHub Actions (`.github/workflows/tests.yml`) runs on every PR and on main: `chrome` is the whole suite; `iphone-ipad` runs `smoke`, `devices` and `layout-fit` on WebKit (Safari's engine) at iPhone SE, iPhone 15 Pro Max and iPad Pro 11 (`WEBKIT=1` in `playwright.config.js`) and keeps a screenshot of every main screen at Standard and Extra large text as the `screens` artifact. WebKit isn't installed in every environment, so locally `npm test` is Chromium only, plus a `small-phone` project that runs `devices.spec.js` at 375×667. A new screen goes into `SCREENS` in `tests/devices.spec.js`.
- Run `npm test` before pushing app changes. It builds `dist/`, runs the smoke test (Home, Learn and Wine DNA render with no console errors) and, while `bundle.js` still exists, the parity tests against it.

## Structure

`npm run build` (esbuild, `scripts/build.mjs`) writes the deployable site to `dist/`: `index.html`, `app.js`, `_worker.js`, `sw.js`, `manifest.json`, `_headers`/`_redirects`, `icons/`, `logo.png`, `reset.html` and `tweaks-inline.compiled.js`. `app.js` holds React 18 + ReactDOM (npm dependencies, production build, exposed as `window.React`/`window.ReactDOM`), then every `data/*.json` and `prompts/*.txt` file the app reads, inlined as `__VINTEREST_ASSETS__`, then the app sources JSX-transformed and concatenated in the order listed in `scripts/app-sources.mjs`. JSX compiles to `_h` (not `React.createElement`), which applies the reader's text size (`TextSize` in `pwa-textsize.js`). They share one global script scope, as before: a top-level declaration in one file is visible to every later file and to `tweaks-inline.compiled.js`. A new source file goes into that list; a new static file the page needs goes into `STATIC_FILES` in the same file.

`_loadJSON(path)`, `_loadTextSync(path)` and `_loadText(path)` stay synchronous but read from `__VINTEREST_ASSETS__`, never the network. The build collects their paths by scanning the sources, so every call must pass a string literal; the build fails on anything else or on a path that doesn't exist. `index.html` is the template for `dist/index.html`: the build points its bundle `<script>` at `app.js?v=<content hash>`, strips any React CDN tags, and swaps the Google Fonts link for the app's own fonts: `buildFonts` copies the latin and latin-ext faces of Poppins (400–800, 400 italic) and Instrument Serif from `@fontsource` into `dist/fonts/` with a `fonts.css`, so nothing loads from Google, fonts work offline, and tests see the real typeface (`tests/devices.spec.js` fails if Poppins isn't loaded).

The hand-compiled `bundle.js` (with its `/* ---- file.jsx (precompiled) ---- */` markers) and the CDN React tags in the root `index.html` remain only until Cloudflare Pages is switched to build from `dist/`; nothing in the build reads `bundle.js`. Until then the live site still serves `bundle.js`. After the switch, don't edit it; it gets deleted in its own PR.

The repo is flat — file naming carries the separation that folders would normally give:

- **UI files** — `pwa-screens-*.jsx`, `pwa-onboarding.jsx`, `pwa-newflow.jsx`, `pwa-scancards.jsx`, `flow-*.jsx`, `tweaks-panel.jsx`. These are screens/flows: markup, layout, event wiring.
- **Logic modules** — plain `.js` files with no JSX: `pwa-platform.js`, `pwa-store.js`, `pwa-textsize.js`, `pwa-xp.js`, `pwa-mastery.js`, `pwa-content-engine.js`, `pwa-grape-learning.js`, `pwa-quiz-questions.js`, `pwa-winedna.js`, `pwa-match.js`, `pwa-scan.js`, `pwa-prefs.js`, `pwa-mywines.js`, `pwa-learnnext.js`, `pwa-guides.js`, `pwa-knowledge.js`, `pwa-palate.js`, `pwa-vinny.js`, `pwa-wines.js`, `pwa-regional.js`, `pwa-userdata.js`, `pwa-backup.js`, `pwa-account.js`, `pwa-install.js`, `pwa-sync.js`. These own state shape, scoring, and content generation, and read the static data in `data/*.json` through `_loadJSON` (inlined at build time).
- **Scores and WineDNA** — scores use Robert Parker's 100-point scale: `ParkerScale` in `pwa-winedna.js` owns the band labels, the score colour bands (`tone`: good 90+, neutral 80-89, bad below 80, drawn by `scoreCol` in `pwa-components.jsx` as green, amber and red on WineDNA and My Wines alike) (96+ Extraordinary, 90–95 Outstanding, 80–89 Very good, 70–79 Average, below 70 Below average), the rating quick-picks and the thresholds WineDNA reads (90+ loved, under 80 didn't work). Any new rating control or score label goes through it. `WineDNA` in the same file computes everything on the WineDNA tab (one high/medium/low scale for every trait label, grape names (`WineDNA.grape` is the one name a grape goes by everywhere: label synonyms and local names or clones (Sangiovese Grosso and Prugnolo Gentile are Sangiovese, Spanna is Nebbiolo), then the spelling on the 50-grape Learn list, so WineDNA, unlocks, quizzes, articles and XP never disagree; Primitivo and Zinfandel are both on the list, so they stay separate), preference signals, favourites, value, journey, the facts the Claude summary may use; What You Love is `WineDNA.loves`, on the user's own scale rather than a fixed 90: from `LOVES_MIN` (6) scored wines of the type, their usual score and best/lowest thirds, style traits (the match engine's `signals` first, then their best third against their lowest), what lifts and holds back their scores (every grape, region, country, producer, price band and age, as points against their average, shrunk by `SHRINK_K` phantom average bottles, listed by lift × √bottles, a grape and region that are the same bottles shown once), each described in words (`favs`/`nots`: grapes, regions and producers first; style via `WineDNA.styleWords`, recurring flavours via `WineDNA.flavourWords` over `WineDNA.NOTE_CLUSTERS`, the evidence in plain terms and their best bottles), a one-line `portrait`, and whether price or age moves their scores. It has no section of its own: it feeds `summaryFacts`, so the written summary's What You Love and What Didn't Work at the top of the tab say it in two sentences, and the facts chip "Region you love most" comes from it; Your House Wines (`WineDNA.houseWines`: had more than once, marked to buy again or hearted, never one scored under 80, most-returned first, each with Restock) replaced Buy Again; How Well We Know You (`TasteMatch.calibration`: from `CAL_MIN` (8) scored wines of the type, each matched again from the others alone against the score given: how often within `CAL_CLOSE` (3) and 5 points, a strip of every miss, which way it leans, and the biggest surprises either way (`SURPRISE`, 5+ points): loved more than expected, and let you down); names with their year via `WineDNA.nameYear`, never "Mlavac 2016 2016"); the screen only renders it, and `ExploreNext` reads the same profile. A wine's body/tannins/acidity are Claude's label estimates, not the user's tasting, so copy distinguishes "the wines you choose" from "what you love" (scores).
- **Matching and the scan flow** — `TasteMatch` in `pwa-match.js` is the only match model: scan result, wine list and wine detail all call it (`calcMatchScore` is a thin wrapper returning its percentage). It predicts the Parker score the user would give a wine from every wine of that type they've scored, weighted by how alike it is (`_predict`: style distance via `WineDNA.axisValue` with `STYLE_SCALE`, a wine nothing like it keeping `STYLE_FLOOR`; same grape ×`GRAPE_X` (4); same region ×`REGION_X` (2), the knowledge-base region via `Regions.resolve`, so a Brunello counts their Chianti and Bolgheri; same producer ×`PRODUCER_X` (3), `_sameProducer`, so an Antinori Brunello counts their Tignanello; buy again ×`BUY_X`), pulled toward their average when evidence is thin and nudged by WineDNA's signals. Another vintage of the same wine they've scored (`WineHistory.otherVintage`: `same` but for the year, both dated) outweighs all of that: their average for those years is `VINTAGE_W` (80%) of the expected score and of `chance`, it's the first reason ("You gave the 2019 a 100. Vintages vary, but it's the same wine."), the summary and the first line of "Why N%?", and it's enough to predict without `MIN_SCORED`; the two years stay two wines in My Wines. There is no cut-off (an earlier top-3 version swung from 91% to 69% on the same bottle when a slightly different label reading swapped which wines counted), so a small change in the style estimates only nudges weights. It returns a verdict, reasons and a confidence. The match % is the score we expect them to give it ("93% match" means about a 93), so it always agrees with "Likely Outstanding for you". Beside it, `chance` is how likely they are to love it (90+): the share of their scored wines of that type they loved, each weighted by how alike it is, pulled toward their overall share when little is alike ("You've loved 77% of wines like it"). Verdicts follow the expected score: `SURE_HIT` (94)+ "Likely a favourite", and 90–93 too when `chance` is at least `HIT_AT` (3 in 4), otherwise "A good bet" like `GOOD_FROM` (87)–89; 80–86 "Could go either way"; under 80 "Probably not for you". `breakdown` is the "Why N%?" panel on the scan result and wine detail (`MatchBreakdown` in `pwa-scancards.jsx`), in plain terms: their average for the type, then which of this wine's traits bring it up or hold it back in their own scores (its producer, its grape, its region, its style, the traits their 90+ wines share), the wines most like it counted out loud ("you loved 6 of the 8 reds most like it; not X (87), Y (80)"), and the expected score and chance of loving it. Price never moves the match: `TasteMatch.priceNote` adds a separate line when a wine costs at least `PRICE_WARN_X` (2×) the top of what they usually spend on that type (the middle half of the prices of the wines they chose, from 4 priced wines; before that, their onboarding usual spend), saying so and that it doesn't change the match. The % stays inside its verdict's band (`PCT_BANDS`), and the "you'd rate it …" line keeps the absolute Parker band. Below 3 scored wines of the type it says "too early to call" and gives no number; never invent a score (the wine list once hashed names into fake ones). `ScanFlow` in `pwa-scan.js` holds the scan screen's non-UI state: rescan identity (`WineHistory.find`/`same` match a wine saved under a slightly different name, a producer spelled differently ("Biondi-Santi"/"BiondiSanti"), or a scan that missed the vintage, which takes the saved bottle's year; a rescan also keeps the saved reading of the label (`ScanFlow.STABLE_FIELDS`: style, grapes, region), so the same bottle gets the same match every time; two different years stay two wines; `WineHistory.getAll` merges duplicates that slipped through, a vintage-less entry into its one dated twin), when to ask "Is this it?" (label `confidence` medium/low), scan XP (awarded only once the wine is confirmed), price context, and Blind Call guesses pre-filling the tasting taps. The label and list prompts live in `prompts/label-scan.txt` and `prompts/list-scan.txt`. The list prompt reads only name, type, region, grape and style, so a wine saved from a list has no tasting notes, pairings and often no grapes: its screen fills them in once (`ScanFlow.fillDetails`, purpose `wine_details`, `prompts/wine-details.txt`; added grapes are `grapes_basis: 'typical'`) and saves them onto the wine. Tasting-note pills and pairing icons take the wine type's colour, and every note starts with a capital (`WineDNA.capNotes`, applied in `cleanWine` so saved wines are fixed on read). Sliders (the score, Blind Call) are `TrackSlider` (`pwa-scancards.jsx`): it answers a touch anywhere on the bar, not only on the knob, because iPhone Safari's own range input only drags from the knob (parked at the far left before a score), so a missed touch swiped the card deck instead. A scan never falls back to a sample wine: without a camera the user picks a photo. Beside the shutter, the gallery button is an icon (`Icon n="gallery"`), and on the other side a torch toggle (`Icon n="torch"`/`torchOn`, `applyConstraints({advanced:[{torch}]})`) in both Bottle and Wine List mode, shown only when the camera track reports `torch` in `getCapabilities()` (Android Chrome; iPhone Safari doesn't let a web page use the torch, so it's hidden there); on the first `Flags.GALLERY_HINT_TIMES` (3) visits with a live camera the framing pill says "Or pick a photo from your gallery ↓" for a few seconds and the button pulses (`useGalleryHint` in `pwa-screens-main.jsx`; `tests/camera.spec.js` uses a fake camera). A "Save for later" scan (`scan_intent: 'checking'`) stays out of WineDNA's "wines you choose" (`WineDNA.chosen`) until they say they bought it or score it; Home's "Waiting on you" card asks. After a score, only quick optional extras (`TastingExtras`): `buy_again`, what they paid (`price_paid`, used by Value and the budget) and where they had it (`where_had`: shown on the wine, searched in My Wines, told to Vinny and the article brief). Each saves as it changes, and the score saves on Save rating, so abandoning the extras or Keep learning never loses the rating. There's no "What did you notice?" step any more; `tasted` (used by `WineDNA.axisValue`) now comes only from a Blind Call. A wine's price everywhere (`WineDNA.priceOf`: WineDNA's average, Value, the script budget, My Wines) is what they paid, else the shop price the Price tab found (`shop_price`, saved onto the wine by `fetchRetailEstimate`), else the label's rough `price_usd`. `grapes` holds variety names only: `WineDNA.cleanGrapes`/`cleanWine` split phrases like "Blend - likely Grenache, Syrah, or Cinsault" into varieties with `blend` and `grapes_basis: 'typical'` (guessed, not on the label), applied on scan intake and in `WineHistory.getAll`; a guessed grape is never announced as new. `times_consumed` is how many times they've had the wine: only `WineHistory.track` raises it, and not for a rescan within `SAME_OCCASION_MS` (12 hours) of the last one; scoring (`add`/`rate`) never does. A wine opened from a suggestion (`source: 'suggestion'`) or a reminder (`'history'`) isn't a scan and isn't saved until the user acts on it. Wine types (`_TYPES` in `pwa-screens-wineiq.jsx`) have a `label` for sentences ("your 6 Outstanding reds") and a `tab`, the singular name on tabs, pills and row titles (Red, White, Rosé, Sparkling…); tapping a type with no wines on WineDNA opens its tab, which says what to scan. Wine-type colours (`_TYPE_COLORS` in `pwa-screens-wineiq.jsx`) colour sliders and selections for that wine; primary buttons stay brand crimson. The shop price shown after a scan comes from `fetchRetailEstimate` (the label's `price_usd` is the placeholder and fallback). Partner shops (`docs/affiliates.md`): `Shops` in `pwa-regional.js` reads `data/retailers.json` (Awin `publisherId`; each shop's `awinMid`, `domains`, `country`, `search` with `{q}`, `enabled`) and `Shops.link(url, placement)` is the one way a shop link is built: tracked through Awin (`awin1.com/cread.php`, `clickref` = `price`/`restock`/`listing`/`explore`) only when both IDs are set, otherwise the plain link (tests set `window.VINTEREST_RETAILERS`). `FindOnline.target/label/open` send "Find it for me" ("Restock" for a buy-again wine, on the Price tab and WineDNA's House Wines) to the first switched-on shop for the user's country, else Google. The live price search also returns where it found the wine (`shops`, up to 3; `_listedShops` in `_worker.js` keeps a shop only if the search returned a page on its site, never a search engine), shown on the Price tab as "In shops now" in the order found. Every tracked link carries `PartnerTag` ("Partner"); money never moves a match, verdict, pick or the order of a list. Tests: `tests/shops.spec.js`.
- **Onboarding and preferences** — `NewUserFlow` (`pwa-newflow.jsx`): welcome (`WelcomeScreen` in `flow-welcome.jsx`: five slides (`_WELCOME_TILES`, every headline ending in a full stop) with Next, dots and Skip (to the last), ending on "Scan your first bottle". Swiping is the screen's own (pointer events, `touch-action: pan-y` on the track and each slide): one swipe moves one slide either way, decided by how far the slides moved and the finger's last speed, never the release position (a cancelled touch has none); the browser's snap scrolling let one flick fly through every slide. The last slide's red dot walks down the timeline on arrival (`_WelcomeTimeline`). Slides 1-4 are a headline, a line of body and a preview of the real screen: the scan result's match (`WineIdentity`, `MatchRing`, `MatchReasons`, with one reason for and one against), WineDNA (`DnaTitle`, `DnaFacts`, `DnaTasteCard`), Vinny on Home (the real `VinnyBar` and `VinnyAnswers` over `onboarding-home.jpg`, the sample user's Home as the app draws it, captured by the generator and faded behind: the question types into the bar, it sends, "Thinking…", the answer types out), and a Written for you card with a slice of the mastery map (`ShelfCard`, `MasteryAreaCard`); slide 5 is the timeline. The previews render those shared components (the screens use the same ones) from `data/onboarding-sample.json`: one imaginary Rioja-loving red drinker branching into the Rhône, and what the app's own engines produced for them, captured by `npm run sample:onboarding` (`scripts/onboarding-sample.mjs`), which also asks Vinny the slide's question for real (`Vinny.prompt` from that user's WineDNA, sent once through the app's `/claude`, `VINNY_ENDPOINT`) and saves the answer (`source: 'vinny'`, or `'placeholder'` until it has reached the proxy); `tests/onboarding.spec.js` fails if the engines now say something different, so rerun it after changing matching or WineDNA. Previews are pictures, never controls: `inert`, no pointer events, a `role="img"` sentence for screen readers, no storage reads or network. Each is drawn at the width that shows it largest and scaled down to fit (`_WelcomePreview`); below 65% (`_WELCOME_PREVIEW_MIN`) it's cropped at the bottom with a fade instead. Each preview plays when its slide arrives (`_WELCOME_CSS`: the match counts up and its reasons fade in, WineDNA's bars grow, Vinny's question and answer type out, the Learn bars fill; a cropped preview scrolls down and back once); reduced motion shows them finished, and nothing changes a preview's size while it plays. No Pro or paywall in onboarding. The slides' own text has set sizes (px strings) that the reader's text-size setting leaves alone, stepped down together (never below 80%) only if they don't fit. "Already have an account? Sign in" (when sign-in is configured) opens `WelcomeSignIn`: the emailed code, then `Sync.welcomeBack()` brings the account down; an account that finished onboarding before goes straight to Home, anyone else carries on with onboarding, signed in) → age confirmation and location (`OnboardSetup`, country guessed from the time zone/language) → first scan → that bottle's story (`FirstScanStory` in `pwa-scancards.jsx`, skippable) → three questions (`OnboardTaste`) → Home. The first scan is the end of onboarding, not a scan log: its deck (`CardDeck` with `firstScan`) opens on "Your match, from your own taste" (`MatchComingSoon`: a meter of scored wines of that type out of `TasteMatch.MIN_SCORED`, what unlocks, and a clearly labelled Example match, never presented as theirs), and the cards where a feature belongs carry a `FeatureNote` (`_FIRST_NOTES`: why-you'll-like-it gets personal, the grape and region quizzes this scan opened, why play Blind Call, the sommelier script, value from what they pay); the last card starts their WineDNA with a score and continues onboarding (`RatingPanel` `onFinish`). Going back from the questions reopens the deck on the score already given (never the picker beside a meter that already counts it), and the questions' "saved in My Wines" note shows once, then fades. `FirstScan` (`pwa-scan.js`) works out those facts. Later scans that are still too early to match show the same meter (compact) on the result. No sign-up or paywall: there are no real accounts or purchases yet, and Pro is offered at the scan limit or on a Pro feature. `UserPrefs` (`pwa-prefs.js`) owns the answers and only asks what the app uses: location sets `vinterest_region`/currency; wine types break ties for the type WineDNA opens on (`UserPrefs.openingType`: the type they've scanned most, then the tab they last picked in the session) and cover someone with no wines yet; usual spend is the price range when there aren't enough priced wines (`SommelierScript.budget`, the scan result's "within your usual spend"); experience lets enthusiasts/experts skip the on-ramp gate on Learn and sets article depth (`{{depth}}` in `prompts/gen-article.txt`). Don't add a question without wiring its answer to something. The profile screen shows these four, each saying what it changes; location ("Where You Buy Wine", `UserPrefs.setLocation`) is the only place region and currency are set, since country, region and currency must change together. Profile is also where sign-in, Backup, install, text size, Travel Mode and the error log live (there's no separate Settings screen; `#settings` opens Profile).

More can be stored than the allowance (unlocked while Pro was on, merged by sync or a backup), so never read `get().unlocked` to decide what's open. Tests: `tests/unlock-cap.spec.js`. `data/knowledge.json` covers the major regions (~57) with checked facts, and each of the 50 Learn grapes with its `profile` and `famousIn` plus one checked line per quiz angle (`aka`, `climate`, `winemaking`, `food`, `ageing`, `lookalike`, `blends`), its `origin`, famous `wines` and how its bunch `look`s, which `grapeFactsText` (`pwa-content-engine.js`) turns into the facts line for grape quizzes and articles (a new grape needs all of them: `tests/quiz-mastery.spec.js` checks); region quizzes and articles only exist for regions there, so add a region (with aliases) rather than letting Claude invent facts. Wine Basics has a topic for every wine type (`data/quiz-bank.json`: red_grapes, white_grapes, rose, sparkling, orange, sweet_fortified, plus general topics). `LearnNext` (`pwa-learnnext.js`) builds the "Keep learning" tiles shown after rating (and after Save for later): the type's basics, the region, the grape, the next on-ramp article, unread articles on this region/grape; only what isn't finished.
- **Learn tab layout** — a sticky row of section chips (For you, Basics, Regions, Grapes, Skills, Mastery) jumps to each section, and no section runs long: `ShowMore` in `pwa-screens-quiz.jsx` shows the first few items (3 articles, 4 Wine Basics topics, 3 regions, `GRAPE_PILLS` grapes) with "Show N more". - **Backend** — `_worker.js` is the entire backend: a Cloudflare Pages Worker (advanced mode) that handles `/claude` (the Anthropic proxy) directly and serves everything else as static assets. There is no `functions/` directory — its presence used to make Cloudflare ignore file-based Pages Functions entirely anyway, so the `/api/retail` (Supabase cache + Apify) and `/api/lcbo` (LCBO) routes it once held were dead code, not a working backend. Retail/price has no third-party API: the label-scan prompt's `price_usd` field is the first guess, and `fetchRetailEstimate` in `pwa-regional.js` does the lookup. Premium wines (label estimate of `PRICE_SEARCH_FROM_USD`, $40, or more) go to purpose `price_search`: `handlePriceSearch` in `_worker.js` writes its own prompt from the wine's fields (never from the client), runs one Anthropic web search of current shop listings in the user's market (the basic `web_search_20250305` tool for speed, `user_location`, `max_uses: 2`). The app waits at most 20 seconds (`PRICE_WAIT_MS`): a slower search returns `pending` and finishes in the background (`ctx.waitUntil`), so its answer is saved for the next open. A search that finds nothing isn't repeated from that device for a week (`searchedAt`, `SEARCH_MISS_RETRY_MS`). The answer is shared between all users for 30 days in the KV namespace bound as `PRICE_CACHE` (setup: `docs/price-cache-setup.md`; without the binding, Cloudflare's per-data-centre cache). Everything else, and any search that finds nothing, gets the ordinary estimate (purpose `price`), whose prompt warns that remembered prestige prices are out of date. Results carry `source: 'search'|'estimate'`, and the screens say which ("in shops now" vs "est."). `_worker.js` is the only place a third-party API key (`ANTHROPIC_API_KEY`) may live — there's no Supabase or Apify integration left to need `SUPABASE_*`/`APIFY_API_TOKEN`. User data will sync to Supabase (`supabase/`): `migrations/0001_user_data.sql` holds `wines` (one row per bottle, keyed by WineHistory's identity), `user_docs` (`xp`, `settings`, `progress`: the backup's sections), and `entitlements`/`usage_counters` (written only by the server). Row-level security keeps every row to its owner; `npm run test:db` checks that on a throwaway local Postgres. The publishable key (`SUPABASE_PUBLISHABLE_KEY`) is public, but the secret key (`SUPABASE_SECRET_KEY`) is a Cloudflare secret for `_worker.js` only; setup steps are in `supabase/README.md`. ## Rules

- **Back follows the way they came.** `nav(to)`/`back()` in `pwa-app.jsx` keep a stack of the screens on the way back (a deep link opens above Home). Going to a screen already on it (a quiz's "Back to Learn", Home from anywhere) returns to it, rewinding the browser's history to that entry (`history.go`) instead of stacking a copy, so the in-app arrow and the phone's back gesture (popstate, which follows the same stack) always agree: from Learn after a quiz, both go Home. `pushed` counts the entries this visit added, so a rewind never leaves the app. Tests: `tests/navigation.spec.js`.
- **Full-screen layout.** `#root` is pinned to the screen's edges (`position:fixed; inset 0` in `index.html`) and the app inside it is `height:100%`; never size the app from `100vh`/`100dvh`/`innerHeight`. On an iPhone home-screen app the status bar style must stay `default` (`apple-mobile-web-app-status-bar-style` in `index.html`): with `black-translucent`, iOS 18 starts the app under the Dynamic Island but still takes the status bar's height off the bottom, so the last 59pt sat outside the app (and stretching the app to cover it only got it clipped). Profile's "Screen details" (`InstallApp.screenInfo`) shows what a real phone reports. Screens keep their content clear of the notch and home indicator with `env(safe-area-inset-top/bottom)` padding (the bottom nav and full-screen footers already do). Safari paints the strip behind the home indicator (and any toolbar gap) with the page's own background, so `pwa-app.jsx` keeps `html`/`body` the colour of whatever is at the bottom of the screen (dark under the welcome and camera screens, white under the nav). `tests/devices.spec.js` checks the app reaches the bottom edge and the page background follows the screen.
- **Text size.** Set font sizes as numbers (`fontSize:15`): `_h` raises anything below 13px to 13 and scales it by the reader's choice on Profile (Standard, Large +10%, Extra large +20%). Only text scales. A string size (`'15px'`) stays exactly as written; use it only for text that must fit a fixed graphic or a fixed-width slot (the score ring, the XP badge beside the logo, the bottom navigation's tab labels, the Text size picker's labels, the welcome tiles). Check a new screen at Extra large on a 375px-wide phone.

- **One name per thing when grouping.** Anything the label can spell several ways is grouped, counted, compared and matched under its one canonical name, never the raw label text: grapes through `WineDNA.grape(g)`, regions through `WineDNA.region(w)` (the knowledge-base region via `Regions.of`: Côtes de Provence and Bandol are Provence, Brunello di Montalcino is Tuscany), so a region or grape never splits into two rows in WineDNA, articles, Journey, Explore Next or matching. A wine's own screens still show what its label says (the appellation), and prompts about one wine may pass its label region. A new region family (an appellation that should count under a bigger region) goes in as an `aliases` entry in `data/knowledge.json`, not as a special case in code. `tests/regions.spec.js` checks the Provence case and fails if shipped code compares, pairs or keys wines by raw `w.region`/`wine.region` (showing "region · country" is fine).
- **Every input earns its place.** If the app asks the user for something (an onboarding answer, a rating detail, a toggle), it must be used to teach, personalise or guide, and the code that uses it should say so. Otherwise don't ask for it. Examples: price paid sets the budget and Value; "buy again" feeds WineDNA's "Worth buying again", matching and the sommelier script; tasting taps adjust `WineDNA.axisValue`.
- **Teach while asking.** Vinterest exists to take the fear out of wine. Anything that shows or asks about body, tannins, acidity and the like explains the word and how to notice it (the wine screen's style sliders with their "?" and one-line meanings); don't assume wine vocabulary.

- **UI changes stay in UI files.** Screens never read or write storage (use the owning module, or `Store`/`Cache` from a logic module); don't add scoring logic or prompt construction directly to a screen beyond what's needed to call an existing logic module — route new stateful behavior through `pwa-xp.js`/`pwa-mastery.js`/`pwa-content-engine.js`/`pwa-grape-learning.js` (or a new module of the same shape) instead of inlining it in the screen.
- **Logic lives in separate modules**, not inline in screens. If a screen starts accumulating its own data-shape decisions (see `WineHistory` in `pwa-wines.js` or `XPSystem` in `pwa-xp.js` as the pattern to follow), pull it out into a logic module with a `KEY`, `get`/`save`, and named operations, the same way the existing stores do.
- **No native project folders are hand-edited.** `ios/` and `android/` are generated by `scripts/native.mjs` and git-ignored; they are never edited by hand — all native-side configuration goes through `capacitor.config.json` (including its `vinterestNative` settings, applied by `scripts/native-config.mjs`), Capacitor plugins, or documented build hooks, never direct changes inside the generated Xcode/Gradle project. Camera access (`getUserMedia` in `pwa-screens-main.jsx`) and the service worker (`sw.js`) both assume a standard web/PWA context and will need review before any Capacitor wrap — see the audit notes in git history for specifics.
