## Process
- The version shown in Wine DNA (below Data Backup) is generated at build time as `<package.json version> (<build number> · <commit>)`, e.g. `v1.3.0 (214 · 2ba108e)`, so every deploy is identifiable without a manual bump. Don't hand-edit a version string into `pwa-screens-wineiq.jsx`; it renders `__APP_VERSION__`. Bump `version` in `package.json` only for a release worth naming. The build number is `BUILD_NUMBER` if set, otherwise the commit count on HEAD; a shallow clone shows the commit alone.
- Run `npm test` before pushing app changes. It builds `dist/`, runs the smoke test (Home, Learn and Wine DNA render with no console errors) and, while `bundle.js` still exists, the parity tests against it.

## Structure

`npm run build` (esbuild, `scripts/build.mjs`) writes the deployable site to `dist/`: `index.html`, `app.js`, `_worker.js`, `sw.js`, `manifest.json`, `_headers`/`_redirects`, `icons/`, `logo.png`, `reset.html` and `tweaks-inline.compiled.js`. `app.js` holds React 18 + ReactDOM (npm dependencies, production build, exposed as `window.React`/`window.ReactDOM`), then every `data/*.json` and `prompts/*.txt` file the app reads, inlined as `__VINTEREST_ASSETS__`, then the app sources JSX-transformed and concatenated in the order listed in `scripts/app-sources.mjs`. They share one global script scope, as before: a top-level declaration in one file is visible to every later file and to `tweaks-inline.compiled.js`. A new source file goes into that list; a new static file the page needs goes into `STATIC_FILES` in the same file.

`_loadJSON(path)`, `_loadTextSync(path)` and `_loadText(path)` stay synchronous but read from `__VINTEREST_ASSETS__`, never the network. The build collects their paths by scanning the sources, so every call must pass a string literal; the build fails on anything else or on a path that doesn't exist. `index.html` is the template for `dist/index.html`: the build points its bundle `<script>` at `app.js?v=<content hash>` and strips any React CDN tags.

The hand-compiled `bundle.js` (with its `/* ---- file.jsx (precompiled) ---- */` markers) and the CDN React tags in the root `index.html` remain only until Cloudflare Pages is switched to build from `dist/`; nothing in the build reads `bundle.js`. Until then the live site still serves `bundle.js`. After the switch, don't edit it; it gets deleted in its own PR.

The repo is flat — file naming carries the separation that folders would normally give:

- **UI files** — `pwa-screens-*.jsx`, `pwa-onboarding.jsx`, `pwa-newflow.jsx`, `pwa-scancards.jsx`, `flow-*.jsx`, `tweaks-panel.jsx`. These are screens/flows: markup, layout, event wiring.
- **Logic modules** — plain `.js` files with no JSX: `pwa-xp.js`, `pwa-mastery.js`, `pwa-content-engine.js`, `pwa-grape-learning.js`, `pwa-quiz-questions.js`, `pwa-winedna.js`, `pwa-match.js`, `pwa-scan.js`, `pwa-prefs.js`, `pwa-mywines.js`, `pwa-learnnext.js`, `pwa-guides.js`, `pwa-knowledge.js`, `pwa-vinny.js`. These own state shape, scoring, and content generation, and read the static data in `data/*.json` through `_loadJSON` (inlined at build time).
- **Scores and WineDNA** — scores use Robert Parker's 100-point scale: `ParkerScale` in `pwa-winedna.js` owns the band labels (96+ Extraordinary, 90–95 Outstanding, 80–89 Very good, 70–79 Average, below 70 Below average), the rating quick-picks and the thresholds WineDNA reads (90+ loved, under 80 didn't work). Any new rating control or score label goes through it. `WineDNA` in the same file computes everything on the WineDNA tab (one high/medium/low scale for every trait label, grape names (`WineDNA.grape` is the one name a grape goes by everywhere: label synonyms, then the spelling on the 50-grape Learn list, so WineDNA, unlocks, quizzes, articles and XP never disagree; Primitivo and Zinfandel are both on the list, so they stay separate), preference signals, favourites, value, journey, the facts the Claude summary may use); the screen only renders it, and `ExploreNext` reads the same profile. A wine's body/tannins/acidity are Claude's label estimates, not the user's tasting, so copy distinguishes "the wines you choose" from "what you love" (scores).
- **Matching and the scan flow** — `TasteMatch` in `pwa-match.js` is the only match model: scan result, wine list and wine detail all call it (`calcMatchScore` is a thin wrapper returning its percentage). It predicts the Parker score the user would give a wine as a similarity-weighted average of their own scores for that type (style distance via `WineDNA.axisValue`, same grape ×2, same region ×1.5, pulled toward their average when evidence is thin, nudged by WineDNA's signals), and returns a verdict, reasons and a confidence. Below 3 scored wines of the type it says "too early to call" and gives no number; never invent a score (the wine list once hashed names into fake ones). `ScanFlow` in `pwa-scan.js` holds the scan screen's non-UI state: rescan identity (`WineHistory.find`/`same` match a wine saved under a slightly different name), when to ask "Is this it?" (label `confidence` medium/low), scan XP (awarded only once the wine is confirmed), price context, the quick-vs-deck preference, and Blind Call guesses pre-filling the tasting taps. The label and list prompts live in `prompts/label-scan.txt` and `prompts/list-scan.txt`. A scan never falls back to a sample wine: without a camera the user picks a photo. A "Save for later" scan (`scan_intent: 'checking'`) stays out of WineDNA's "wines you choose" (`WineDNA.chosen`) until they say they bought it or score it; Home's "Waiting on you" card asks. After a score, optional taps record how the wine compared with the label estimate (`tasted`, used by `WineDNA.axisValue`), what they paid (`price_paid`, used by Value) and `buy_again`. `grapes` holds variety names only: `WineDNA.cleanGrapes`/`cleanWine` split phrases like "Blend - likely Grenache, Syrah, or Cinsault" into varieties with `blend` and `grapes_basis: 'typical'` (guessed, not on the label), applied on scan intake and in `WineHistory.getAll`; a guessed grape is never announced as new. `times_consumed` is how many times they've had the wine: only `WineHistory.track` raises it, and not for a rescan within `SAME_OCCASION_MS` (12 hours) of the last one; scoring (`add`/`rate`) never does. A wine opened from a suggestion (`source: 'suggestion'`) or a reminder (`'history'`) isn't a scan and isn't saved until the user acts on it. Wine-type colours (`_TYPE_COLORS` in `pwa-screens-wineiq.jsx`) colour sliders and selections for that wine; primary buttons stay brand crimson. The shop price shown after a scan comes from `fetchRetailEstimate` (the label's `price_usd` is the placeholder and fallback).
- **Onboarding and preferences** — `NewUserFlow` (`pwa-newflow.jsx`): welcome → age confirmation and location (`OnboardSetup`, country guessed from the time zone/language) → first scan → three questions (`OnboardTaste`) → Home. No sign-up or paywall: there are no real accounts or purchases yet, and Pro is offered at the scan limit or on a Pro feature. `UserPrefs` (`pwa-prefs.js`) owns the answers and only asks what the app uses: location sets `vinterest_region`/currency; wine types pick the type Home and WineDNA open on; usual spend is the price range when there aren't enough priced wines (`SommelierScript.budget`, the scan result's "within your usual spend"); experience lets enthusiasts/experts skip the on-ramp gate on Learn and sets article depth (`{{depth}}` in `prompts/gen-article.txt`). Don't add a question without wiring its answer to something. The profile screen shows these four, each saying what it changes.
- **Learning from a scan** — a confirmed scan opens its grape (`GrapeUnlocks.unlockViaScan`, via `GrapeUnlocks.key`, which maps label names through synonyms onto the 50-grape allowlist) and its region (`RegionUnlocks`, `Regions.resolve` in `pwa-content-engine.js`, matching region/sub-region/name against each knowledge-base region and its `aliases`); 5 of each free (`FREE_GRAPE_CAP`, `FREE_REGION_CAP`), then Pro, with locked ones shown as "Unlock with Pro" (Learn hub, shelf articles, Keep learning). `data/knowledge.json` covers the major regions (~57) with checked facts; region quizzes and articles only exist for regions there, so add a region (with aliases) rather than letting Claude invent facts. Wine Basics has a topic for every wine type (`data/quiz-bank.json`: red_grapes, white_grapes, rose, sparkling, orange, sweet_fortified, plus general topics). `LearnNext` (`pwa-learnnext.js`) builds the "Keep learning" tiles shown after rating (and after Save for later): the type's basics, the region, the grape, the next on-ramp article, unread articles on this region/grape; only what isn't finished.
- **Learn tab layout** — a sticky row of section chips (For you, Basics, Regions, Grapes, Skills, Mastery) jumps to each section, and no section runs long: `ShowMore` in `pwa-screens-quiz.jsx` shows the first few items (3 articles, 4 Wine Basics topics, 3 regions, `GRAPE_PILLS` grapes) with "Show N more". Read articles leave the shelf for the collapsed "Your library"; completed quizzes collapse behind their toggle. Wine Basics follows the wine types first (red, white, rosé, sparkling, orange, sweet & fortified), then regions, tasting and food: that's the order of `data/quiz-bank.json`.
- **Wine Skills and Mastery** — `Guides` (`pwa-guides.js`, content in `data/guides.json`) are fixed-text guides in five groups (tasting, ordering out, buying, food pairing, hosting): three sections, three questions (QuizMastery set `guide:<id>`), one "For you" line computed from the reader's wines (`Guides.personal`, no Claude call) and something to try in the app. A guide is finished once read and every question is right. `KnowledgeMap` (`pwa-knowledge.js`) is Mastery, the Pro screen `mastery-map`: every area scores only from reading and passing, never from scans or scores. Wine types (basics quiz, unlocked grape quizzes of that colour, articles about the type), Regions and Grapes (each unlocked one: 70% its quiz, 30% articles about it), and one area per skill group (guides and beginner articles read, guide questions passed). `summary()` is the free teaser on Learn (overall, strongest, biggest gap). Concept Check and Words You've Met are gone from Learn; `MasterySystem` stays only for Blind Call's concept flags.
- **Home and Vinny** — Home (`pwa-screens-home.jsx`) is "what next", top to bottom: Ask Vinny, Waiting on you, Up next (`LearnNext.home`: a first scan for a new user, otherwise the next unread Written for you piece, the next beginner article, the step that closes their biggest Mastery gap, the next Wine Skills guide; one main card and two more), Written for you, Recently scanned, Your WineDNA (a line per type they drink, an Explore Next pick, a link to the sommelier script in WineDNA) and their knowledge (level, XP, Mastery teaser). The sommelier script itself lives in WineDNA only. `Vinny` (`pwa-vinny.js`, prompt `prompts/vinny.txt`, purpose `wine_qa`) answers from `Vinny.profile` (their WineDNA per type, best and disliked wines, buy again, usual spend, recent bottles), keeps the last two turns for a follow-up, remembers recent questions, and `learnLink` adds one "Learn more" link without another call: an unlocked grape or region quiz, the Pro offer when the free allowance is the only reason it's locked, else a Wine Skills guide on the topic. A tapped suggestion fills the box; only the arrow sends.
- **My Wines** — `MyWines` (`pwa-mywines.js`) decides what the list shows: type and status filters (Unscored, Saved for later, Buy again), search, sorts, month groups for Recent, and the summary line (prices via `WineDNA.priceOf`, in the user's currency). The screen renders compact `WineRow`s: swipe left for Edit/Delete (Delete has Undo via `WineHistory.restore`), "Score it" opens the rating.
- **Written for you** — every Learn shelf piece is personal, and the app says so wherever one appears (Learn shelf, WineDNA's "Written from your WineDNA", wine detail's Learn tab, Keep learning, the article itself). `ContentEngine` in `pwa-content-engine.js` owns it: `pickArchetype` takes the kind of piece the shelf has least of (never five "From Rioja to…"s), `compareRegion` only compares a region with one where they drink the same type, `_rotate` heals untouched repeats on old shelves, `because(stub)` is the "Because you gave X a 95" line, and `readerBrief(stub)` gives the article prompt their related bottles (score, price, buy again, how it compared with the label), plus WineDNA facts and usual spend for the piece's own wine type only (`_subjectType`: a white-grape piece never draws on their reds; only "Entering <type>" adds what they mostly drink, for contrast). One Claude call per article, cached with its `forYou` line; don't add per-view calls.
- **Shared primitives** — `pwa-components.jsx` holds both UI atoms (`Card`, `Btn`) and cross-cutting logic (`WineHistory`, `Regional`, the taste-match scorer). Treat the logic objects in this file as belonging to the logic layer even though the file extension says otherwise — don't add new UI-only code here; put new UI atoms in a screen file or a new UI file, and new stateful logic in a new `.js` module.
- **Backend** — `_worker.js` is the entire backend: a Cloudflare Pages Worker (advanced mode) that handles `/claude` (the Anthropic proxy) directly and serves everything else as static assets. There is no `functions/` directory — its presence used to make Cloudflare ignore file-based Pages Functions entirely anyway, so the `/api/retail` (Supabase cache + Apify) and `/api/lcbo` (LCBO) routes it once held were dead code, not a working backend. Retail/price is Claude-only now: the label-scan prompt's `price_usd` field and `fetchRetailEstimate` in `pwa-components.jsx` (see the UI rules below) are the whole feature, exactly as shipped. `_worker.js` is the only place a third-party API key (`ANTHROPIC_API_KEY`) may live — there's no Supabase or Apify integration left to need `SUPABASE_*`/`APIFY_API_TOKEN`. If a real `/api/*` backend is needed later, it has to be added inside `_worker.js` itself (or via `_routes.json` to let Pages Functions back in) — not as a new `functions/` directory that silently never runs.
- **Data** — `data/*.json` is static reference content (XP curve, quiz bank, grape allowlist, knowledge base, and `explore-styles.json`, the curated catalogue behind WineDNA's Explore Next, read by `ExploreNext` in `pwa-content-engine.js`). Not user data — ships inside `app.js` and is read-only at runtime.
- **Build and tests** — `scripts/` (build, file list, a static server for tests) and `tests/` (Playwright: `smoke.spec.js`, `parity.spec.js`, `build.spec.js`, `quiz-mastery.spec.js`, `sommelier-script.spec.js`, `explore-next.spec.js`, `find-online.spec.js`, `winedna.spec.js`, `scan-flow.spec.js`, `onboarding.spec.js`, `mywines.spec.js`, `learn-next.spec.js`, `written-for-you.spec.js`, `learn-hub.spec.js`, `mastery.spec.js`, `home.spec.js`). `dist/` is build output and is gitignored.
- **Dead/prototype files** — `screens-core.jsx`, `screens-detail.jsx`, `screens-growth.jsx`, `screens-modes.jsx`, `wireframe-kit.jsx`, `design-canvas.jsx`, `pwa-scan-home-temp.jsx`, `Vinterest-App-Bundle.jsx`, `flow-auth.jsx`, `flow-paywall.jsx`, `pwa-onboarding.jsx` (the old sign-up, paywall and onboarding screens, kept for the `New User Flow.html` prototype), and the standalone `*.html` prototypes are not part of `bundle.js` and are not shipped. Don't assume something is live just because it's in the repo — cross-check against `APP_SOURCES` in `scripts/app-sources.mjs` first.

## Rules

- **Every input earns its place.** If the app asks the user for something (an onboarding answer, a rating detail, a toggle), it must be used to teach, personalise or guide, and the code that uses it should say so. Otherwise don't ask for it. Examples: price paid sets the budget and Value; "buy again" feeds WineDNA's "Worth buying again", matching and the sommelier script; tasting taps adjust `WineDNA.axisValue`.
- **Teach while asking.** Vinterest exists to take the fear out of wine. Anything that asks about body, tannins, acidity and the like explains the word and how to notice it (see `_NOTICE` in `pwa-scancards.jsx`); don't assume wine vocabulary.

- **UI changes stay in UI files.** Don't add `localStorage` reads/writes, scoring logic, or prompt construction directly to a screen beyond what's needed to call an existing logic module — route new stateful behavior through `pwa-xp.js`/`pwa-mastery.js`/`pwa-content-engine.js`/`pwa-grape-learning.js` (or a new module of the same shape) instead of inlining it in the screen.
- **Logic lives in separate modules**, not inline in screens. If a screen starts accumulating its own data-shape decisions (see `WineHistory` in `pwa-components.jsx` or `XPSystem` in `pwa-xp.js` as the pattern to follow), pull it out into a logic module with a `KEY`, `get`/`save`, and named operations, the same way the existing stores do.
- **No native project folders are hand-edited.** This repo has no `ios/`/`android/` directories today. If the app is ever wrapped with Capacitor, those generated native projects are never edited by hand — all native-side configuration goes through `capacitor.config.json`, Capacitor plugins, or documented build hooks, never direct changes inside the generated Xcode/Gradle project. Camera access (`getUserMedia` in `pwa-screens-main.jsx`) and the service worker (`sw.js`) both assume a standard web/PWA context and will need review before any Capacitor wrap — see the audit notes in git history for specifics.

## Backlog
- **Country courses and Travel prep** (shown on Learn as "Coming soon", Pro): a country course assembles everything for one country from content we already have or write once (its regions from `data/knowledge.json`, its grapes, local wines and label terms, the matching quizzes and guides) into one ordered course that counts towards Mastery. Travel prep: the user says where they're going in a short prompt; we assemble the country course plus local wine recommendations from their WineDNA and the quizzes to be ready for the trip (and set Travel Mode prices). Mostly prewritten content; Claude only picks and orders it and writes the short trip plan.
- **Wine Lists**: Create and manage named lists (e.g. "Want to Try", "Restaurant picks"). "Add to List" button removed from Wine Detail → Data tab pending full build-out.
- **Anthropic prompt-caching**: `_worker.js`'s /claude proxy now sends a distinct, fairly stable prompt template per `purpose` (see the CLAUDE_PURPOSE_LIMITS table). Most of these are a large fixed instruction block plus a small variable part (the specific wine, the specific quiz answer). Worth adding `cache_control` to the fixed portion of each purpose's prompt to cut cost and latency — cache hits are shared across all users hitting the same purpose, not per-user, so it scales with traffic. Do this after the core migration (auth/sync/Capacitor) is stable, not before — it's a cost/speed optimization, not launch-blocking.
- **Spaced repetition for question-set quizzes**: region, Wine Basics and grape quizzes share `QuizMastery` (`pwa-quiz-questions.js`): each quiz draws 5 questions, unanswered first then least-recently-served review, and a set completes once every question has been answered correctly at least once (region banks: `RegionQuizBank` in `pwa-content-engine.js`; grape banks: `pwa-grape-learning.js`). What's missing is decay: a completed set stays complete forever, unlike `MasterySystem`'s box/interval/`nextDue` for concepts. Revisit once the core migration is stable if completed sets should resurface for re-testing.
